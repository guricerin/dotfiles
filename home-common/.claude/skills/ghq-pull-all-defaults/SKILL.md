# 全リポジトリのデフォルトブランチを最新にする

ghq で管理している全リポジトリ（ghq root 配下）のデフォルトブランチを、まとめて origin に追いつかせる。本人の作業中のブランチや修正を壊さずに、手元を最新にしておくため。

## 停止条件（最優先）

次のどれかに当てはまったら、作業を進めずに止まり、「停止時の報告」の形でユーザーに返す。推測で埋めて先に進まない。

- **わからない**:
  - 一部のリポジトリだけを対象にするよう言われたが、どれを指すか決められない（例: 「仕事のやつだけ」で、owner で分けてよいか分からない）
- **矛盾している**:
  - ユーザーが「未コミットの修正をコミットして」「stash して」など、このスキルの「やらないこと」に当たる操作を求めている。このスキルの外で別の作業として行うか確認する
- **承認が必要**:
  - 該当なし（理由: 行うのは fetch と、fast-forward でしか進まないデフォルトブランチの更新だけで、作業中のブランチや修正は変わらず、外部への送信もないため）
- **想定外**:
  - `ghq` が見つからない、またはスクリプトが例外で終わった
  - 全リポジトリが `failed` になった（ネットワークや SSH の認証が使えない可能性が高い）

一部のリポジトリだけが `skipped`・`failed` になった場合は止まらない。結果の報告にまとめて書く。リポジトリごとに事情が違い、1つのために全体を止めると使いにくいため。

### 停止時の報告

- 事実: 確認できたこと（出典: ファイル名・コマンドの出力・ユーザーの発言）
- 推測: 事実から推測したこと（根拠つき）
- 止まった理由: 上のどの停止条件に当たるか
- 決めてほしいこと: 選択肢と、それぞれを選んだときの影響

## 事実と推測の扱い

- 推測には「推測:」と明記し、根拠を添える。出典を示せないことは事実として書かない
- 推測を前提に、取り消せない操作をしない
- `failed` の原因は、スクリプトが出したエラーメッセージだけから書く。メッセージから原因を推し量るときは「推測:」をつける

## 入力

- 対象: `ghq list --full-path` が返す全リポジトリ。ユーザーからの入力は基本的にない
- 並列数（任意）: スクリプトの `--jobs`。指定がなければ 8
- 確認だけ（任意）: 「何をするか見るだけ」と言われたら `--dry-run` を付ける。fetch も更新もせず、予定だけを出す

## 手順

1. **スクリプトを実行する。** 各リポジトリでやることは決まりきっていて判断が要らないので、エージェントではなくスクリプトで並列に処理する（速く、トークンも使わず、結果の形式も毎回同じになるため）。

   ```bash
   bash ~/.claude/skills/ghq-pull-all-defaults/scripts/pull_default_branches.sh [--jobs 8] [--dry-run]
   ```

   スクリプトはリポジトリごとに次のように動く。

   | 状況 | すること |
   |---|---|
   | origin のリモートがない | 何もせず `skipped` |
   | 今のブランチがデフォルトブランチで、未コミットの修正がある | 何もせず `skipped`（本人の指示） |
   | 今のブランチがデフォルトブランチで、修正がない | `git fetch` → `git merge --ff-only origin/<default>` |
   | 今のブランチがデフォルトブランチではない | `git fetch origin <default>:<default>` で、移動せずにデフォルトブランチだけを進める。今のブランチと未コミットの修正はそのまま |
   | ローカルにデフォルトブランチがない | `git fetch` だけ（ブランチは作らない） |

   - デフォルトブランチは `origin/HEAD` から取る。なければ `git ls-remote --symref origin HEAD` で問い合わせる（設定は書き換えない）
   - 未追跡のファイル（`.env` など）は「未コミットの修正」に数えない。数えると、未追跡のファイルを置いているリポジトリがいつまでも更新されないため。fast-forward で上書きされる場合は git 自身が止めて `failed` になる
   - fast-forward できない（ローカルのデフォルトブランチに独自のコミットがある）場合は、何も変えずに `failed` になる
   - SSH のパスフレーズや認証の入力待ちで止まらないよう、`BatchMode=yes` と `GIT_TERMINAL_PROMPT=0` で実行し、fetch は60秒で打ち切る

2. **結果を読む。** 出力は1リポジトリ1行のタブ区切り（`状態  リポジトリ  今のブランチ  詳細`）。状態は `updated`・`up-to-date`・`fetched`・`skipped`・`failed`・`dry-run` のどれか。全件が `failed` なら停止条件に従う。

3. **会話で報告する。** 下の「出力先」の形で返す。本人が知りたいのは「手を動かす必要があるリポジトリ」なので、`skipped` と `failed` を先に、理由つきで書く。

## 出力先

会話に、次の順で短く返す。ファイルには書き出さない。

1. 件数: 全 N 件のうち、更新 / 最新 / fetch のみ / スキップ / 失敗 の件数
2. 失敗したリポジトリ: リポジトリ名・今のブランチ・エラーの要約。推測した原因と、本人がやるとよいことがあれば「推測:」をつけて添える
3. スキップしたリポジトリ: リポジトリ名と理由（例: デフォルトブランチに未コミットの修正がある）
4. 更新したリポジトリ: リポジトリ名と、どのブランチを更新したか。件数が多ければ名前だけを並べる
5. 未コミットの修正を残したまま、デフォルトブランチだけを更新したリポジトリがあれば、その一覧（修正には触れていないことが分かるように）

`up-to-date` のリポジトリは件数だけでよい。

## 終わりの条件

次がすべて確認できたら完了。停止条件で止まった場合は完了ではない。

- スクリプトが終了コード 0 で終わり、`ghq list` の件数と同じ行数の結果を出した
- `skipped`・`failed` のリポジトリをすべて、理由つきで報告した

## やらないこと

このスキルの中では、承認があっても次のことはしない。必要な場合は、スキルの外で別の作業としてユーザーに指示してもらう。

- 未コミットの修正をコミット・stash・破棄する（本人の作業を勝手に履歴に残したり消したりしないため）
- 今のブランチを切り替える（switch・checkout）
- fast-forward できないブランチを、merge・rebase・reset・`+` 付きの fetch で無理に合わせる
- push する
- ブランチを作る・消す、`origin/HEAD` などの設定を書き換える
- サブエージェントで各リポジトリを並列に処理する（スクリプトで足りるため）
